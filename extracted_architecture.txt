1. Objective and Design Philosophy
This project is a business entity-resolution system. Source 1 is the deduplicated reference source; for every Source 1 record, the system must find zero, one, or multiple matching Source 2/Source 3 records. The official metric is macro F₀.₅, so the architecture is deliberately precision-first. The system must also correctly identify singletons, retain every test Source 1 entity, treat country as open-set, and use only the supplied challenge data.
Core principle: candidate generation, feature engineering, pair classification, threshold selection, and final output construction are separate modules. Never let one stage silently perform another stage's job.

9. Stage 5 — Training Pair Construction
Positive pairs come from the supplied ground truth. Negatives must include both easy and difficult cases.
Random negatives.
Same/similar name + different address.
Same/similar address + different name.
Same city/locality + similar name.
Top TF-IDF candidate known to be a non-match.
High-scoring false positives mined from a first model.
Hard-negative mining loop: train baseline → score candidate negatives → select high-probability false positives → add them to training → retrain. This directly teaches the model to separate visually similar but distinct businesses.
10. Stage 6 — Entity-Aware Validation
Split by complete Source 1 entities, not individual pair rows.
Start with 80% train / 20% validation.
Save validation S1 IDs and the random seed.
Do not leak candidate pairs from the same S1 into both sets.
If sufficient data exists, use entity-aware cross-validation for model selection.
Use validation for all threshold, ensemble-weight, and safety-rule decisions.

13. Stage 9 — Requested Hybrid Hyperparameter Strategy
Use two complementary hyperparameters jointly: α, the XGBoost/LightGBM blending weight, and τ, the final match threshold. This is the core hybrid optimization. Instead of assuming that either model or threshold is best, search the pair (α, τ) directly against validation macro F₀.₅.
Hybrid probability:
P_hybrid = α × P_XGB + (1 − α) × P_LGBM
Hyperparameter
Search
Purpose
α
0.00, 0.01, …, 1.00
Controls model contribution
τ
0.50, 0.51, …, 0.99; refine by 0.001
Controls precision/recall operating point
Joint search procedure
Train the selected XGBoost configuration.
Train the selected LightGBM configuration.
Store validation probabilities from both models.
For each α, calculate P_hybrid.
For each α and τ, construct match predictions.
Compute macro F₀.₅ at Source 1 entity level, including singletons.
Select the highest validation F₀.₅ pair (α*, τ*).
Refine α and τ around the best coarse result.
Freeze α* and τ* for test inference.
Important: α and τ are hyperparameters, not guaranteed values. The validation data decides the final pair.
14. Why the Hybrid Can Improve Accuracy
XGBoost and LightGBM can make different errors even with the same features. A weighted probability blend can reduce model-specific variance. The threshold then converts the blended probability into a precision-focused decision. The combination is useful only if validation F₀.₅ improves; otherwise use the stronger single model.
15. Stage 10 — Calibration (Optional)
Test probability calibration only if raw probabilities are unstable. Candidate methods include Platt/logistic calibration or isotonic regression. Calibration must use a separate calibration portion where possible. Keep it only if the final macro F₀.₅ or stability improves.
16. Stage 11 — Precision Safety Layer
If P_hybrid < τ → reject.
If name evidence is weak, require stronger independent address evidence.
If address evidence strongly contradicts the candidate, penalize/reject only if validation supports the rule.
Never force a match merely because it is the top candidate.
Allow multiple matches when multiple candidates independently satisfy the final decision rule.
Do not impose a one-to-one constraint: the challenge explicitly allows zero, one, or many matches.
17. Stage 12 — Singleton / Abstention Logic
For each S1, sort candidates by P_hybrid and let p1/p2 be the top two.
If p1 < τ → empty matched_entity_ids.
Optionally use p1−p2 as a confidence-margin feature/guard; validate before using.
Do not force the best candidate for weak evidence.
Measure singleton false positives separately.
18. Stage 13 — Optional Small Model Verifier
Only after the tree pipeline is strong, test a small open-source model as a verifier for borderline pairs. It must comply with the challenge's stated license and ≤8B parameter requirement. It must use only the supplied record information, never external business data. Route only uncertain pairs to it. Keep it only if validation macro F₀.₅ improves.
19. Stage 14 — Error Analysis
Separate blocking failures from classifier failures.
List false positives with highest model probability.
List false negatives with highest evidence but rejected decisions.
Group errors by name-only, address-only, both, missing fields, source and country.
Convert recurring false-positive patterns into hard negatives or new features.
Re-run the fixed validation split after each controlled change.

25. Non-Negotiable Mistakes to Avoid
Do not compare every S1 against every S2/S3 if blocking can reduce the search space.
Do not rely on exact names only.
Do not use only random negatives.
Do not optimize ordinary accuracy instead of macro F₀.₅.
Do not use a fixed 0.5 threshold without validation.
Do not force one match per S1.
Do not hard-code countries to US/India.
Do not let candidate generation silently remove true matches.
Do not keep an ensemble unless validation proves improvement.
Do not use external lookup or enrichment.
Do not tune α/τ from the public leaderboard instead of held-out validation.
